Reflection — LoanLens
What I Built
LoanLens is an end-to-end machine learning system that predicts the probability a loan applicant will default, built on the Home Credit Default Risk dataset. The problem is one real financial institutions face constantly: deciding, with limited information available at application time, whether an applicant is likely to repay. Beyond producing a risk score, the project explains why the model made that prediction using SHAP, and it's deployed as a live Streamlit app, so the whole pipeline is actually usable — not just a notebook that runs once on my machine and never again.

The mini-extension I chose was a Fairness Audit — computing Disparate Impact Ratio and Equal Opportunity Difference across gender and age groups. I chose this specifically because a credit risk model that's accurate overall but systematically biased against a protected group isn't something I'd feel comfortable calling "done." It also connected naturally to the explainability work I was already doing with SHAP: once I could see which features drove predictions, the obvious next question was whether those drivers affected different groups differently.

What I Learned About the Tools
Scikit-learn Pipelines and ColumnTransformer do something simple but easy to get wrong without them: they guarantee identical preprocessing at train time and prediction time. Before understanding this properly, I didn't appreciate how easy it is to accidentally leak test-set information into training, or to have training and serving quietly drift apart. What surprised me: how much of "doing ML properly" is really about avoiding invisible mistakes like this, not about picking a fancier model.

SHAP attributes a model's prediction to individual features, either for one row or in aggregate. What surprised me: SHAP values for tree models come out in log-odds space, not raw probability — so the numbers on a waterfall chart don't literally match a displayed percentage elsewhere in the app. I'd tell a friend: don't assume the axis numbers are the probability itself; understand the direction and relative size of each bar, that's the genuinely useful part.

LightGBM and Optuna — LightGBM trains fast and handles imbalanced tabular data well out of the box. Optuna's job is simple: run many trials with different hyperparameter combinations and find the best one automatically. What surprised me: a 30-trial tuning search only improved ROC-AUC from 0.759 to 0.762 — tuning helps, but it's not a magic lever. The bigger wins in this project came from fixing class imbalance and adding engineered features, not hyperparameter search.

Streamlit turns a Python script into a web app with almost no frontend code. What surprised me: how much of "deploying" isn't about the model at all, it's about small environment differences. My app worked perfectly locally and then failed on Streamlit Cloud with a FileNotFoundError, purely because the app's working directory on the cloud wasn't what I'd assumed. That one bug taught me more about the gap between "runs on my machine" and "actually deployed" than anything else this week.

What I Learned About Myself
The class imbalance problem was harder than I expected, not technically, but in terms of judgment. Getting a model to score well on accuracy is easy; understanding which metric actually matters for a specific real-world problem — recall over precision, since missing an actual defaulter is worse than a false alarm on a safe applicant — was a genuinely useful thing to reason through, and I enjoyed working through that tradeoff.

That same judgment got tested again late in the project: after tuning my model, I tried adding external credit bureau features from a second dataset table. The result improved ROC-AUC, F1, and precision — but recall, the metric that matters most here, actually dropped. It would have been easy to just ship the model with the "better" overall numbers. Instead I stopped, checked my reasoning with my mentor, and kept the version with better recall, documenting the bureau experiment honestly rather than quietly picking whichever model looked more impressive on paper.

Debugging was harder than expected in one specific way: several bugs this week weren't in my model logic at all — they were environment or path issues. A stray typo in a filename. A pandas version quirk breaking a dtype check. A working-directory assumption that only broke once deployed. None of these were "hard" in a deep technical sense, but they ate real time, and I had to get comfortable reading tracebacks calmly instead of getting frustrated by them.

I enjoyed the explainability and fairness work most — it's where the project stopped being just "get a good accuracy number" and started being about whether the model is actually trustworthy. I liked it least when I was stuck on git divergent-branch issues, which had nothing to do with ML at all and just ate time I wanted to spend building.

On schedule: I moved noticeably faster in the back half of the project than the front half, largely because deadline pressure clarified priorities. That tells me I work well under a close, clear deadline — but I'd like to build the habit of applying that same focus earlier, without needing the deadline to force it.

What I'd Do Differently
If I started over, I'd centralize my feature engineering logic into a single shared function from day one instead of copy-pasting the same transformations across notebooks. I hit a real bug — a ValueError in my SHAP notebook — purely because two notebooks had drifted out of sync on which columns existed. A shared function would have made that structurally impossible.

I'd also test my Streamlit app's file-loading logic with an eye toward "what if this runs from a different working directory" before deploying, not after. I wish my mentor had told me on Day 1 to spend the first hour of any deployment task specifically thinking about environment differences between local and cloud, rather than assuming correct logic locally guarantees correct behavior once deployed.

What's Next — The 3rd Year Plan
This project is the seed of my 3rd year ML portfolio, not a one-off. The clearest next steps are already partially scoped: properly integrating the bureau.csv features I tested (recovering recall, likely through explicit threshold tuning combined with the added signal, rather than accepting the tradeoff as-is), expanding the fairness audit to more protected attributes and intersectional analysis, and building a lightweight monitoring/retraining loop so the model doesn't silently go stale over time. I want to use the next year to turn this from "a project that works" into "a project I understand deeply enough to defend in an interview" — which is exactly what the 3rd Year Roadmap below lays out.
